## State at handoff

This session ran a **broad, 9-way parallel bug audit** across the entire `theoses2` monorepo (56 findings), triggered by two real production bugs found earlier the same day (a `homedir()`/`process.cwd()` path-resolution bug in `memory-store.ts` and the Telegram bot's session-orphaning bug — both already fixed and released as v1.0.4–v1.0.7 before the broad audit started). The 56 findings were filed as 9 grouped tracking issues, **#112–#120**, one per audited area.

Codex (a separate coding-agent session/tool) was then handed each issue to fix, with this session acting as **independent reviewer** — every PR was code-reviewed for real (read the actual diff, traced the logic by hand, ran tests myself) before being accepted, never just trusted from Codex's own completion report. That caught two real regressions:
- **PR #122** (issue #112): the `usesDefaultSessionDir()` fix only threaded the new `agentDir` parameter through `SessionManager.create()`, not `.open()`/`continueRecent()` — meaning it broke on the common *resume* path, misfiring a UI warning far more often than the original bug did. Sent back, fixed properly (all three construction paths), re-verified.
- **PR #125** (issue #115): the Telegram stop/queue fix silently dropped an already-queued follow-up message with no user notice, plus had a stale-flag risk that could silently eat an unrelated future message. Sent back, fixed with a better design than the minimum ask (message-ID-scoped tracking instead of chat-wide), re-verified by actually running the new regression test, not just trusting the report.

**Result**: issues #112–#118 and #120 are fully fixed, reviewed, merged (PRs #122–#128, #130), and released as **v1.0.9** (tagged and pushed; VPS auto-updater not explicitly confirmed live at end of session — check `readlink -f /opt/theoses2-releases/current` next session if it matters).

## What's actually left on #119 (agent package / harness)

PR #129 fixed, tested, and merged: `agent-loop.ts`'s abort-mid-batch tool-result-pairing corruption (both sequential and parallel paths — though only sequential got a dedicated regression test, worth adding one for parallel too), `compaction.ts`'s missing stopReason filter, `session/context.ts`'s same filter gap, `harness/events.ts`'s unguarded listener calls, `branch-summarization.ts`'s budget-check ordering, `edit-diff.ts`'s over-eager fuzzy matching, and `bash.ts`'s discarded abort cause.

**Explicitly NOT touched, and these are the real remaining work for #119:**
- `packages/agent/src/harness/agent-harness.ts:305-508` — the `AgentHarness` class (meant to implement the durable-lane surface described in `packages/agent/docs/harness.md` Parts 3-5) is almost entirely stubbed — `prompt`, `compact`, `navigateTree`, `resume`, `abort`, `steer`, `followUp`, `cancelQueued`, `waitForIdle`, `createLane`, etc. all just reject with `HarnessNotImplemented`.
- `packages/agent/src/harness/tools/file-mutation-queue.ts:20-26` — `getMutationQueueKey` uses the canonical (realpath) path when a target file exists but falls back to the raw absolute path when it doesn't; two concurrent calls on the same logical file across a symlinked path segment can silently fail to serialize writes.
- `packages/agent/src/harness/tools/path-utils.ts:16-30` — `resolveReadToolPath` silently substitutes unicode-normalization/quote/space path variants with no logging, can silently read a different file than requested.
- `packages/agent/src/harness/session/jsonl/repo.ts:198-232` — TOCTOU: `sessionIdExists` then `fs.writeFile` with no exclusive-create flag can silently overwrite an existing session file under concurrent creation from a second process.
- `packages/agent/src/harness/reducer.ts` — implements a record-log model structurally different from `harness.md`'s documented register/`op.state` model. Internally consistent, but unauditable against the doc as written.

**The actual blocker for all five of the above**: `harness.md` §1.7 self-acknowledges "the incompatible format-4 code... is unfinished" — meaning most of the doc's Parts 1-4 (transactions, registers, operation state machine, effect sandwich, abort/close, migrate-on-open) currently have **no implementation to check bugs against**. This isn't a bug-fixing task, it's an open architectural question: is `harness.md`'s spec aspirational future-work that the current `agentLoop`/append-log session model is meant to eventually be replaced by, or should the doc be rewritten to describe what's actually built? That decision has to be made (by the user, or by a session explicitly scoped to make it) before file-mutation-queue.ts/path-utils.ts/repo.ts/reducer.ts can be meaningfully "fixed" rather than patched around a design that might not be the final one.

**Recommended first move next session**: don't hand Codex a vague "finish #119" prompt — it'll stall on the ambiguity (see Corrections below, this is exactly the failure mode that's bitten before). Either (a) make the architectural call yourself/with the user first and then write Codex a concrete prompt referencing the decided design, or (b) scope a narrower, self-contained slice (e.g. just the `file-mutation-queue.ts` realpath-fallback fix, which doesn't depend on the bigger harness-vs-doc question) and leave the rest for a dedicated design session.

## Corrections made this session (don't repeat these mistakes)

- **Never trust a subagent/Codex completion report without independently verifying.** Reconfirmed hard today: Codex's own "Completed issues #112-#120" summary message did *not* actually include the fixes for the #122/#125 regressions this session had already flagged — the branches were untouched (same single commit, same timestamp) despite the completion report implying everything was done. Caught only by checking `gh pr view --json commits` directly, not by trusting the prose summary.
- **A "review, don't rubber-stamp" instruction pays off in direct proportion to how much you actually read.** All 9 first-round reviews (and both re-reviews) were done by forking a fresh reviewer agent per PR, each told explicitly to read full files (not just the diff), trace logic by hand for the highest-risk changes, and actually run tests rather than trust the PR body's claimed test results. Both real regressions found this session (#122, #125) were things a diff-skim would have missed — the bugs were in code paths adjacent to what was touched (`.open()`/`continueRecent()` never got the same treatment as `.create()`; the queue-fix's interaction with an *already-queued* message wasn't the scenario originally asked about) rather than in the changed lines themselves.
- **When deliberately deferring architectural work (like #119), say so explicitly and get it filed correctly** — this session correctly kept #119 open with a clear "why," but did *not* correctly reflect the equivalent partial-completion state on #118 (which has 3 deferred items but no open child issue or edited body reflecting that). Do that bookkeeping step in the same sitting as the deferral decision, not as an afterthought.
- **A broad multi-area audit is genuinely worth running after finding one bug, not just fixing the one instance.** The two bugs that kicked off this whole session (`memory-store.ts`, Telegram `process.cwd()`) turned out to have 4 more unfixed instances of the exact same pattern elsewhere in the codebase (`episodic-store.ts`, `memory-consolidation.ts`, `dashboard/index.ts`, `dashboard/memory-graph.ts`) — all found by the audit, none of which would have been caught by just fixing the original two and moving on.
