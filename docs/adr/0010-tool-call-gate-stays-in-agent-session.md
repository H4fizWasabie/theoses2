# The tool-call gate and result handling stay in AgentSession

Every tool call passes `AgentSession._gateToolCall` before it runs (owner PreToolUse hooks, extension `tool_call` handlers, then the file checkpoint) and `_afterToolCall` after it (extension `tool_result` handlers, image normalization, then owner PostToolUse hooks). The main agent installs them as its `beforeToolCall` / `afterToolCall`, and the `task` sub-agent receives the same two functions. An architecture review on 2026-10-04 proposed a tool-call pipeline module owning these steps behind ports, citing churn (#439, #447, #504, #508 each changed them) and two agents using them. We decided not to do it.

The seam already exists: `AgentOptions.beforeToolCall` and `afterToolCall` in the agent package, and both agents already plug in one shared implementation. They are two callers, not two adapters, so a module would give callers nothing they do not have. It fails the deletion test the way ADR-0009 did: about 85 lines would move behind five ports (command hooks, hook context, extension runner, file checkpoints, the image setting) without hiding a decision. The churn is already local: each of those changes added or removed one step inside one of the two methods and was covered by one session suite (command hooks, tool result images, file rewind, task tool), and the session harness is cheap to run.

Revisit when a third agent needs the gate with a different set of steps, when a step needs state AgentSession does not have, or when one change starts having to touch both methods and their callers together.
