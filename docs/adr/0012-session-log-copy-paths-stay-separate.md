# Session-log copy paths stay separate

Four paths copy a session log's entries into another log: rotation (`SessionManager.rotate`), branching (`createBranchedSession`), `--fork` (`SessionManager.forkFrom`) and `/import` (`importFromJsonl`, through `copySessionLog`). Each has to carry its saved images, because an image reference in the log is relative to the session's own artifact directory (`artifacts/<session id>/`), which a copy under a new id or in another sessions directory does not have. An architecture review on 2026-10-14 proposed one copy module that all of them would go through, owning the image move. We decided not to do it.

It fails the deletion test. The paths do not copy the same way. Rotation keeps only the live entries and marks the old log; branching keeps the path to one leaf and rebuilds its labels; both restore the images of what they copy and let the new log save them under its new id. Fork copies the whole tree under a new id and cwd, restoring and re-saving one entry at a time to bound memory. Import keeps the id, so it copies the log file and its `images/` directory as they are (`copySessionImages`). What they share is one rule, where the source's images are, so a module would move little behind an interface and leave the rest where it is.

The review did find the cost of keeping them separate: fork and import had both forgotten the images (a forked or imported session showed "[image unavailable]"). The fix gives the two paths that read another log one rule for where that log's images are (`sourceArtifactDir`: beside the log first, else the default sessions directory for its cwd), and each path has a test that copies a session with an image and finds the bytes in the copy. The known cost: the `artifacts/<session id>` layout is spelled out in each path, so a change to it touches all four.

Revisit when a fifth copy path appears, or when one change has to touch all of them, such as a change to the artifact layout or a new kind of file that lives beside the log.
