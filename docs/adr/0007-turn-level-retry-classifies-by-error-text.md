# Turn-level retry classifies failures by error text

theoses-ai has two retry classifiers with the same name. `utils/provider-retry.ts` decides request-level retries from the HTTP status and `x-should-retry`, mirroring the OpenAI/Anthropic SDKs. `utils/retry.ts` decides from the error text with a regex, and backs both `isRetryableAssistantError` (turn-level retry) and the OpenAI Codex raw-fetch loop. On the same response they can disagree: a 500 "billing account exhausted" is retryable by status and not by text, and a 400 "Please retry your request" is the reverse. An architecture review proposed one classifier over a structured failure (`{status, kind, code}`) recorded on every `AssistantMessage`. We rejected it.

Request-level retry is opt-in. `retryProviderRequest` defaults to zero retries, Codex's `DEFAULT_MAX_RETRIES` is 0, and no deployment sets `retry.provider.maxRetries` (checked 2026-09-26: production, staging and local settings have no `retry` key). The status classifier and the Codex loop therefore never run. The classifier that does run is the turn-level one: AgentSession's retry budget calls `isRetryableAssistantError` on the failed message, the same way for every provider. Adding a new retryable failure there is one pattern in one list (#341, #352), which has worked each time. A structured failure would change `AssistantMessage` (public), touch every stream implementation, and only replace a text match that is not causing trouble.

Revisit if request-level retry is turned on for a deployment (then the two classifiers' disagreement becomes live), or if a failure turns up that the text classifier can't match reliably, such as two providers producing the same text for failures that need different decisions.
